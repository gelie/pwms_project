# API Reference

PWMS exposes a **REST API** (Django REST Framework) under `/api/`, covering the
workflow registers alongside their audit history:

| Area | Resources |
| --- | --- |
| Identity & structure | users, groups, roles, memberships |
| Workflow registry | workflow types, states, transitions |
| Workflow instances | delegation reports, international resolutions, international agreements, bills, meetings (the Events workflow) |
| History | per-instance auditlog CRUD trail and domain event log |

A django-ninja implementation of the audit endpoint once sat alongside DRF at
`/ninja/` as an evaluation spike; it has been removed, leaving DRF as the single
API stack.

OpenAPI schema and interactive docs are generated by `drf-spectacular`.

---

## 1. Authentication

Three schemes are accepted; all resolve to the same `request.user`, so the
resource permissions below are identical however the caller signed in.

- **Token** (recommended for clients) — `Authorization: Token <key>`. Obtain a
  key from `POST /api/auth/token/` (see below). **Tokens expire**: a key is
  rejected once it is older than `settings.TOKEN_TTL` (`TOKEN_TTL_DAYS`, default
  30 days; `0` disables expiry).
- **Session** — log in via the browsable API `POST /api/auth/login/` (or the web
  login) so the session cookie is used.
- **Basic** — `Authorization: Basic base64(user:pass)`.

`SessionAuthentication` deliberately leads the authenticator list, so an
unauthenticated request is `403` (with an HTML login page on the browsable API)
rather than a bare `401`.

### Token lifecycle

| Method | Path | Auth | Purpose |
| --- | --- | --- | --- |
| POST | `/api/auth/token/` | – | Exchange `username` + `password` for a token |
| POST | `/api/auth/token/refresh/` | ✓ | Delete the caller's token and return a fresh one |
| POST | `/api/auth/token/revoke/` | ✓ | Delete the caller's token (responds `204`) |

`POST /api/auth/token/` is **rate-limited**: an unauthenticated caller is capped
by client IP at `REST_FRAMEWORK["DEFAULT_THROTTLE_RATES"]["token"]`
(`TOKEN_THROTTLE_RATE`, default `20/min`), and a request over the limit is
`429 Too Many Requests` with a `Retry-After` header. That blunts scripted password
grinding without locking out an office sharing one NAT address. (The counters live
in Django's cache, so with several gunicorn workers the per-process `LocMemCache`
lets each count separately — point `CACHES` at Redis/Memcached for an exact limit.)

The TTL is **absolute**, not sliding: using a token does not extend it, so a
client that needs continuity calls `refresh/` (which rotates the key) before the
TTL elapses. `POST /api/auth/token/` re-uses your current key while it is still
valid and rotates it once expired, so it always hands back a usable token; on any
`403` from an expired key, simply obtain a new one. Two housekeeping notes:

- expired tokens fail authentication immediately (`ExpiringTokenAuthentication`)
  but are removed from the database by `python manage.py purge_tokens` — run it
  from a systemd timer / cron (`--dry-run` to preview, `--days N` to override);
- `refresh/` and `revoke/` both delete the existing row, so the old key stops
  working at once.

Credentials are checked by the same backends as the web login (Active Directory,
then the local database). `POST /api/auth/token/` returns:

```json
{
  "token": "9a1f…",
  "user_id": 42,
  "username": "alice",
  "email": "alice@example.com"
}
```

```bash
# Obtain, then call the API with the key
curl -s -X POST http://127.0.0.1:8000/api/auth/token/ \
  -H 'Content-Type: application/json' \
  -d '{"username": "alice", "password": "…"}'

curl -s http://127.0.0.1:8000/api/users/me/ \
  -H 'Authorization: Token 9a1f…'
```

## 2. Endpoints

### API root

| Method | Path | Auth | Purpose |
| --- | --- | --- | --- |
| GET | `/api/` | ✓ | Lists the token endpoints, the resource index and the audit routes |

### Resources

Every resource is keyed by its **`public_id`** (a UUIDv7) so sequential database
keys never appear in a URL. Lists are paginated (`count` / `next` / `previous` /
`results`, 50 per page) and support `?search=` and `?ordering=`.

| Resource | Collection | Detail |
| --- | --- | --- |
| Users | `/api/users/` | `/api/users/{username}/` |
| Current user | `/api/users/me/` | — |
| Groups | `/api/groups/` | `/api/groups/{public_id}/` |
| Roles | `/api/roles/` | `/api/roles/{public_id}/` |
| Memberships | `/api/memberships/` | `/api/memberships/{public_id}/` |
| Workflow types | `/api/workflow-types/` | `/api/workflow-types/{public_id}/` |
| States | `/api/states/` | `/api/states/{public_id}/` |
| Transitions | `/api/transitions/` | `/api/transitions/{public_id}/` |
| Delegation reports | `/api/delegation-reports/` | `/api/delegation-reports/{public_id}/` |
| International resolutions | `/api/resolutions/` | `/api/resolutions/{public_id}/` |
| International agreements | `/api/agreements/` | `/api/agreements/{public_id}/` |
| Bills | `/api/bills/` | `/api/bills/{public_id}/` |
| Meetings | `/api/meetings/` | `/api/meetings/{public_id}/` |

Each collection is a standard `GET` (list) / `POST` (create); each detail URL is
`GET` (retrieve) / `PUT` / `PATCH` (update) / `DELETE`.

**Users are addressed by `username`** (e.g. `/api/users/gelie/`) rather than the
`public_id`: a caller usually holds the ERP username already, so a direct lookup
saves the search-then-fetch round trip. The match is **case-insensitive**, and dots
in a username (the ERP's `firstname.lastname`) are fine. Every other resource
stays on `public_id`.

### User reporting line

`GET /api/users/{username}/` and `GET /api/users/me/` add the reporting line to
the user:

- `supervisor` — the user's manager, as a nested user summary (or `null`);
- `subordinates` — the users whose `supervisor` is this user (their **immediate**
  reports), ordered by surname then given name.

The list endpoint keeps the flat representation (supervisor as a plain row id, no
`subordinates`), so paging through users stays cheap. `supervisor` is writable on
create / update (managers only) for anyone setting the line by hand; the nightly
`sync_users_oracle` also populates it from the ERP `EMPLOYEEID` / `SUPERVISORID`
chain — see [Management Commands](./Management%20Commands.md).

### User memberships

`GET /api/users/{username}/memberships/` returns every group membership the user
holds (the same rows as `/api/memberships/`, but scoped to one user and with the
group and role spelled out). Newest first by default, paginated. All filters are
optional:

| Query param | Effect |
| --- | --- |
| `active` | `true` = current only, `false` = ended only |
| `as_of` | in force on this date (`start_date ≤ as_of`, and `end_date` null or later) |
| `start_after` / `start_before` | start-date window (inclusive) |
| `end_after` / `end_before` | end-date window (inclusive) |
| `group` | only memberships of this group (its `public_id`) |
| `role` | only memberships in this role (its slug) |
| `group_type` | only memberships whose group is of this type |
| `ordering` | `start_date` (default, descending), `end_date`, `is_active`, `group__name`, `role__name` |

```bash
# A user's current committee/ministry appointments on a given date
curl -s "…/api/users/gelie/memberships/?as_of=2024-06-01&group_type=committee" \
  -H "Authorization: Token $TOKEN"
```

A malformed date, UUID or `ordering` value is a `400`; an unknown username is a
`404`.

### Group details + members by name

`GET /api/groups/lookup/` resolves a group from its name — or any part of it —
and returns the group's details **and** its member roster in one call:

| Query param | Required | Effect |
| --- | --- | --- |
| `name` | ✓ | Match groups whose `name` or `short_name` contains this string (case-insensitive) |
| `exact` | – | Require the whole name / short name to match, not a substring |
| `include_inactive` | – | Also list memberships that have ended |

Each match is a `Group` (the fields of `/api/groups/{public_id}/`) plus a
`members` array; each member carries the user's identity (name, email, MP/staff
flags, …), their `role` and the appointment window. Members are active-only unless
`include_inactive=true`, and ordered by surname then given name. A missing `name`
is `400`; no match is an empty `[]`.

```bash
curl -s "http://127.0.0.1:8000/api/groups/lookup/?name=portfolio" \
  -H "Authorization: Token $TOKEN"
```

### Workflow instance actions

Beyond CRUD, every workflow instance (`delegation-reports`, `resolutions`,
`agreements`, `bills`) exposes:

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/{public_id}/transitions/` | Transitions reachable from the current state |
| POST | `/{public_id}/transition/` | Perform one; body `{"transition": "<uuid>", "comment": "…"}` → `201` with the `TransitionLog` |
| GET | `/{public_id}/events/` | Domain `WorkflowEvent` log (append-only) |
| GET | `/{public_id}/audit/` | `auditlog` CRUD history for the instance |

### Meetings (the Events workflow)

`/api/meetings/` is a workflow register like the others (same CRUD, transitions,
events and audit actions), plus the meeting detail a calendar and an attendance
register need:

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/meetings/?meeting_type=&mine=1&member=&start=&end=&search=` | Filter by meeting type, the caller (`mine`), another user by `member=<username>`, a start-date window (`start` / `end`), or free text |
| GET | `/api/meetings/mine/` | The caller's meetings **by membership**: on the attendance register, convener group, chair/secretary, owner or assignee |
| GET | `/api/meetings/calendar/` | A date-window feed (`?start=&end=`) shaped for a calendar UI |
| GET | `/api/meetings/{public_id}/` | The detail, with `attendance`, `attendance_summary`, `meeting_type`, scheduling fields, the on-premises `venue` / `off_site_venue` / `off_site_address` (and the read-only `venue_display`), `attendance_mode` / `attendance_mode_label`, and `calendar_state` |
| GET | `/api/meetings/{public_id}/attendance/` | The attendance register; each row carries `source` / `source_label` (`host_group` or `invitee`) |
| POST | `/api/meetings/{public_id}/attendance/add/` | Add an invitee; body `{"user": <pk>}` or `{"guest_name": "…", "guest_email": "…"}`, plus `capacity`, `is_required` → `201` |
| POST | `/api/meetings/{public_id}/attendance/record/` | Record RSVP and/or attendance; body `{"attendance": "<uuid>", "rsvp_status": "accepted", "attendance_status": "present", "note": "…"}` |
| POST | `/api/meetings/{public_id}/attendance/regenerate/` | Rebuild the register from the hosting group's active members, keeping the invitees (returns the register) |
| POST | `/api/meetings/{public_id}/minutes/` | Advance the minutes status; body `{"status": "draft"|"filed"|"approved"}` |

The web calendar dashboard (`/pwms/meetings/`, `?view=month|week|day` , `&week_start=`) and
its JSON feed (`/pwms/meetings/calendar.json`) mirror the same permission-scoped
query. The feed honours the calendar's week start (its `?week_start=` or
`settings.MEETING_CALENDAR_WEEK_START`): a `?month=` window is widened to the
whole weeks containing the month (as the grid draws them), the entries are
ordered day-first from that week start, and the response reports the
`week_start` it used.

The web calendar also **imports and exports** meetings as CSV/XLSX
(`/pwms/meetings/import/`, `/pwms/meetings/export/`, and
`manage.py import_meetings`) — HTML/download routes rather than API endpoints; the
column format is in [Meetings Import & Export](./Meetings%20Import%20%26%20Export.md).

### HTMX search fragments (HTML, not JSON)

The form search pickers call plain Django views that return HTML rows, not API
responses, so they are deliberately absent from the schema above:

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/pwms/user-search/` | users matching `?search=` |
| GET | `/pwms/group-search/` | groups matching `?search=` |
| GET | `/pwms/country-search/` | countries matching `?search=` (name or ISO code) |
| GET | `/pwms/city-search/` | cities matching `?search=`, scoped by `?country=<pk>` |

They are session-authenticated like every other site route. See
[Search Lookups](./Search%20Lookups.md) for the contract they follow.

The app's other dynamic pages — the dashboard, the workflow detail pages with
their tabs, the SharePoint attachment picker, the alerts page, the report builder
/ exports, the per-instrument documents and the state-machine diagrams — are
likewise server-rendered HTML (or images) under `/pwms/`, not JSON API endpoints
(see [Functional Design](./Functional%20Design.md) and
[System Design → URL map](./System%20Design.md#2-url-map)).

## 3. Permissions

Permission is resolved by `pwms.api.permissions.ResourcePermission`, on top of
the shared resolver in `pwms.services.permissions`:

- **Reading** identity / structure / registry resources (users, groups, roles,
  memberships, workflow types, states, transitions) is open to any signed-in
  user.
- **Creating, editing and deleting** those resources requires the global *manage*
  capability (`Role.can_manage_permissions` on an active membership) or a
  superuser. Privilege flags (`is_staff`, `is_superuser`) and passwords are never
  writable through the API; a password sent on create/update is hashed, never
  returned.
- **Workflow instances** resolve through their own group / Role / State RBAC
  chain (`instance.can(...)`): the owner may view/edit/delete, the assignee may
  view, and a member of a group holding access gets whatever the access row, role
  override and state permission allow. `list` is scoped to what the caller may
  view, so it can never surface a row the detail URL would reject (`403`).
- **Creating** a workflow instance requires holding one of the type's
  `create_roles` in its group (superusers bypass this). Omitting `current_state`
  on create defaults it to the type's initial state.

Anonymous → `403`. Authenticated but not permitted → `403`.

## 4. Response shape — audit history

`GET /api/resolutions/{public_id}/audit/` (and the equivalents
`GET /api/agreements/{public_id}/audit/`, `GET /api/bills/{public_id}/audit/`
and the per-instance `/audit/` action) returns a JSON array of
`auditlog.LogEntry` entries (newest first by default):

```json
[
  {
    "id": 1,
    "action": 0,
    "action_display": "create",
    "actor_email": "alice@example.com",
    "timestamp": "2026-09-09T14:44:33.706015Z",
    "changes": {
      "title": ["None", "A test resolution"],
      "current_state": ["None", "1"],
      "workflow_type": ["None", "1"],
      "resolution_number": ["None", "IR-1"]
    },
    "remote_addr": null
  }
]
```

| Field | Meaning |
| --- | --- |
| `action` / `action_display` | `0/1/2` = create / update / delete (auditlog enums) |
| `actor_email` | who made the change (`null` for anonymous/system) |
| `changes` | dict of `field: [before, after]`; M2M entries have `{"type": "m2m", "objects": […], "operation": "add"}` |
| `timestamp` | when it happened |
| `remote_addr` | client IP captured by the auditlog middleware |

Missing `public_id` → `404`. Anonymous → `403`.

### Examples

```bash
# API root (Basic auth for a quick check)
curl -u alice:pw http://127.0.0.1:8000/api/

# Token auth: obtain, then list the caller's visible bills
TOKEN=$(curl -s -X POST http://127.0.0.1:8000/api/auth/token/ \
  -H 'Content-Type: application/json' \
  -d '{"username": "alice", "password": "pw"}' | python -c 'import sys,json;print(json.load(sys.stdin)["token"])')
curl -s http://127.0.0.1:8000/api/bills/ -H "Authorization: Token $TOKEN"

# Audit history via a session cookie
curl -b cookies.txt -c cookies.txt \
  -X POST -d "username=alice&password=pw" \
  http://127.0.0.1:8000/api/auth/login/
curl -b cookies.txt http://127.0.0.1:8000/api/resolutions/<public_id>/audit/
```

## 5. Serialization

- `AuditLogEntrySerializer` (DRF, `pwms/api/serializers.py`) renders
  `auditlog.LogEntry` rows: `id, action, action_display, actor_email, timestamp,
  changes, remote_addr`. It reads the rows through
  `pwms/utils/audit_helpers.py` (`get_audit_trail_by_public_id`), which filters
  `LogEntry` by ContentType + internal PK.

The resource serializers live in the same module: `UserSerializer`,
`GroupSerializer`, `RoleSerializer`, `MembershipSerializer`,
`WorkflowTypeSerializer`, `StateSerializer`, `TransitionSerializer`, the shared
abstract `WorkflowInstanceSerializer` and its four concrete subclasses,
`TransitionLogSerializer` and `WorkflowEventSerializer`.

## 6. Extending

To expose a new concrete workflow model (the four shipped instruments all have
one; this is the pattern for a future `Motion`):

```python
# pwms/api/serializers.py
class MotionSerializer(WorkflowInstanceSerializer):
    class Meta(WorkflowInstanceSerializer.Meta):
        model = Motion
        fields = WorkflowInstanceSerializer.Meta.fields + [...]


# pwms/api/views.py
class MotionViewSet(WorkflowInstanceViewSet):
    queryset = Motion.objects.all()
    serializer_class = MotionSerializer


# pwms/api/urls.py
router.register("motions", views.MotionViewSet, basename="motion")
# plus, for the standalone audit route:
# path("motions/<uuid:public_id>/audit/", views.MotionAuditHistoryView.as_view(), name="motion-audit-history"),
```

The list-scoping, `perform_create` (`WorkflowType.can_create`) and the
`transitions` / `transition` / `events` / `audit` actions are all inherited from
`WorkflowInstanceViewSet`.

Remember to register the model with `auditlog` in `PwmsConfig.ready()` and add it
to the API root’s resource listing.
